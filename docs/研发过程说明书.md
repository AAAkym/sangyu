# 研发过程说明书

## 一、研发概述

“桑榆智伴”定位为面向空巢老人的智慧监护与康养服务小程序，采用老人端与家属端双角色设计，围绕“健康监测—自动预警—家属响应—服务预约—处置留痕”形成可演示、可审计的照护闭环。

研发采用目标驱动的分批次节奏。基础架构、身份关系和告警闭环先行；随后补齐设备、健康趋势、报告与陪伴能力；夜间批次增加提醒、留言和联系人；最后集中进行适老化、内容合规、品牌和回归审计。现阶段已完成核心闭环与体验打磨，处于可演示、待上线状态。

技术栈为微信小程序原生框架 + 本地 Express 后端（JSON 文件数据库）+ 讯飞 Spark Lite 对话引擎（带降级）+ CSS 变量设计令牌体系 + ec-canvas 图表。这样选择是为了在 MVP 阶段减少基础设施和依赖，快速验证双端流程、告警责任链和适老化交互；请求封装、路由边界和数据集合保持可替换，后期可平滑迁移微信云开发。

## 二、技术架构

### 2.1 分层结构

```text
老人端/家属端小程序
  ├─ 页面层：登录、首页、健康、告警、设备、报告、预约等
  ├─ 工具层：request · auth · voice · healthStatus · polling
  └─ 设计令牌层：颜色、字号、间距、圆角、安全区
                 │ HTTP
                 ▼
Express 后端
  ├─ 路由层：auth/relationship/device/health/alert/appointment/report/chat…
  ├─ 规则引擎：阈值判定、5 分钟去抖、告警状态机
  ├─ 业务工具层：token、日期聚合、字段兼容、降级与限流
  └─ JSON 数据层：server/data/*.json
                 │
                 ▼
外部服务：讯飞 Spark Lite（超时、授权失败或限流时自动降级）
```

### 2.2 数据模型

当前 `server/data/` 实际包含 13 个集合：

| 集合 | 用途 |
|---|---|
| users | 用户档案、角色与创建信息 |
| relationships | 老人与家属的监护关系、授权撤销信息 |
| devices | 设备归属、最后上报时间、电量与解绑状态 |
| health_observations | 心率、血压、血氧等健康观测记录 |
| alerts | SOS/规则告警、状态、证据与处置时间线 |
| appointments | 服务预约及当前状态 |
| reports | 规则生成的健康报告、建议与证据引用 |
| invitations | 邀请码及有效期 |
| reminders | 用药日程提醒（不采集药品、剂量） |
| messages | 家人留言墙内容 |
| contacts | 紧急联系人及分组信息 |
| chats | 陪伴对话留痕与回复来源 |
| sessions | 服务端保存的 session_key（不下发客户端） |

### 2.3 架构设计的关键决策

1. **自定义 tabBar**：微信原生 tabBar 难以按角色动态显示。`custom-tab-bar` 统一维护 tab 定义，再按角色显隐，使老人和家属可共享页面注册，同时避免切换身份时高亮错位。
2. **JSON 文件存储**：MVP 数据量小、结构变化快，JSON 便于演示数据一键重置和批次迭代；接口与业务逻辑保持独立，为迁移云开发保留入口。它不等同于生产数据库方案，正式上线前需替换持久化与并发控制。
3. **聊天三级降级**：依次尝试 Spark Lite、本地陪伴语料库、兜底话术，配合信号量限流（免费版 QPS=2）、流控错误码 11200–11203 识别和超时处理，保证模型不可用、被限流或断网时仍能回应。
4. **共用工具**：健康状态阈值集中在 `healthStatus`，服务端规则引擎复用同一口径，避免老人端、家属端和自动告警出现两份判断。

## 三、研发过程

### 阶段一：基础架构搭建

- **目标**：先建立可运行的双端骨架和稳定的请求边界。
- **做了什么**：初始化原生小程序、Express 服务、页面注册、`custom-tab-bar`、request/auth/voice/healthStatus 工具与暖琥珀设计令牌。
- **关键决策与问题**：采用 Mock/真实双模式，使演示不依赖真实密钥；将颜色、字号和安全区集中为 CSS 变量，减少后续批量调整风险。
- **验证**：完成 JS、JSON、WXML/WXSS 结构校验，前端调用与后端路由逐条对照。
- **产出**：双端页面骨架、统一请求出口、可切换角色入口和首版设计系统。

### 阶段二：身份与监护关系

- **目标**：确保“谁能看谁的数据”有明确关系基础。
- **做了什么**：实现 Mock 建档与真实登录代码、角色更新、6 位邀请码生成/绑定、关系列表、撤销授权和设备级联解绑。
- **关键问题与解决**：真实模式依赖微信 `AppSecret`，密钥仍为占位，因此保留代码就绪但不宣称真机通过。另发现撤销后重绑“返回成功但关系不恢复”：原因是软删除记录被幂等查询命中；修复为过滤已解绑关系，并在命中旧记录时清除 `unboundAt` 复活关系。
- **验证**：角色双向切换、生成→绑定→撤销→重绑闭环实测通过。
- **产出**：可撤回的监护关系链和最小权限基础。

### 阶段三：核心告警闭环

- **目标**：优先交付养老场景中最不可替代的安全责任链。
- **做了什么**：老人端 SOS 长按 1 秒并处理 `touchcancel` 防误触；家属端 15 秒轮询新告警，触发震动、弹窗、语音和红点；后端实现 `open → acknowledged → escalated → external_dispatched → resolved` 状态机、越序拒绝和时间线留痕。
- **关键问题与解决**：状态文案、动作和后端枚举容易分叉，改为集中常量与 `canTransition` 校验；每次变化写入操作人、时间、备注和当前处理人，解决“只推送不留证”的责任缺口。
- **验证**：演示态 4 条告警覆盖 4 种状态组合，告警创建、列表、详情、升级和解决链路均纳入回归。
- **产出**：SOS 与规则告警双来源、可追溯处置时间线和家属提醒闭环。

### 阶段四：智能化能力

- **目标**：让健康数据从展示升级为可解释的预警和陪伴服务。
- **做了什么**：设备上报联动 4 条规则；同规则同老人 5 分钟去抖；实现 7/30 天趋势图、老人端简版 sparkline、规则生成的 AI 健康报告（含数据质量、证据引用和固定免责声明）；将语音页升级为打字聊天。
- **关键问题与解决**：历史健康记录使用 `openid`、设备上报使用 `elderOpenid`，导致趋势图漏数据；路由增加双字段兼容并统一新写入字段。早期 smoke 因去抖状态未重置产生假失败，改为每遍测试前 `demo:reset`，区分测试环境状态与业务缺陷。Spark 诊断返回 `AppIdNoAuthError`（11200），无法据此断言具体授权原因，因此保留本地引擎和兜底，不把模型未通写成已完成。
- **验证**：规则触发、趋势聚合、报告生成与聊天降级均有接口回归；15 项演示链路修正字段名后 15/15 通过。
- **产出**：可连续运行的健康预警、报告和离线陪伴能力。

### 阶段五：设备与关系治理

- **目标**：补齐设备生命周期、关系撤回和隐私边界。
- **做了什么**：支持家属代绑、解绑软删除、越权校验、10 分钟无上报判定离线、电量展示；完善关系列表补全姓名、撤销授权级联解绑设备；加入隐私政策、最小字段和多处医疗免责声明。
- **关键决策**：设备状态由 `lastReportAt` 实时计算，避免存储状态过期；提醒不记录药名和剂量，联系人仅提供快捷拨号并二次确认。
- **验证**：设备在线/离线、电量、解绑、关系撤销和隐私文案逐项核对。
- **产出**：设备和关系的可治理生命周期，以及不越过诊疗边界的产品口径。

### 阶段六：体验打磨与质量保障

- **目标**：降低老人使用门槛，并让演示可复现、回归可持续。
- **做了什么**：落地字号三档、高对比模式、语音开关、112rpx 主操作区、安全区令牌、状态多通道；清理用户可见的 Mock 字样；修复键盘适配、长文本溢出和自定义 tab 高亮；加入 WXML 校验器、视觉审计和 `demo:reset`。
- **典型问题与解决**：批量脚本曾把内容追加到根容器外造成渲染异常，改用结构校验器检测根外残留；`auth` 重写曾覆盖 Mock 路由导致回归，恢复双模式边界；长文本在报告和留言页存在截断风险，补 `overflow-wrap: anywhere`。
- **验证**：WCAG 对比度实算、点击区/字号/安全区/溢出审计全部完成；smoke 122/122 连续两遍，`npm test` 28/28，WXML 19/19。
- **产出**：可复现演示数据、可重复回归流程和适老化质量门禁。

## 四、核心技术创新点

### 1. AI 对话三级降级架构

**问题**：外部模型可能授权失败、超时、断网或触发免费版流控。  
**方案**：Spark Lite → 本地陪伴语料库 → 兜底话术；使用信号量限制并发，识别 11200–11203 流控/服务错误并按超时策略降级。  
**价值**：弱网、无网和模型不可用时服务不中断，且聊天来源可在记录中追溯。

### 2. 告警全生命周期与处置留痕

**问题**：单次推送无法说明谁响应、是否升级以及何时关闭。  
**方案**：SOS 与规则引擎双来源，家属端 15 秒轮询四路提醒，五态状态机集中校验，每次迁移写入操作人、时间和备注。  
**价值**：事件可追溯、可复盘，为养老服务责任界定提供事实记录。

### 3. 适老化与合规并重的设计体系

**问题**：老人对小字号、误触和仅靠颜色表达状态更敏感，同时健康产品容易越过医疗边界。  
**方案**：暖琥珀令牌全站驱动，字号 36/44rpx 档位、高对比、主操作区 112rpx 以上，SOS 长按 1 秒，状态采用颜色+文字+形状，并在报告、提醒、联系人和隐私页面提供免责声明。  
**价值**：降低操作和识别成本，同时明确“健康管理参考、不构成诊断治疗建议”的边界。

### 4. 工程质量保障体系

**问题**：快速批次迭代容易引入字段、结构和视觉回归。  
**方案**：smoke 运行时 122 项连续两遍通过，单元测试 28 项，配合 WXML 结构校验、视觉/对比度/点击区审计和演示数据一键初始化。  
**价值**：把质量检查前置，保证每轮演示状态一致、问题可定位。

## 五、研发验证与成果

### 5.1 功能验证

已验证的核心链路包括：角色切换与关系绑定、SOS 创建与家属推送、规则引擎自动预警、告警状态流转与时间线、健康趋势与老人简版、规则生成的 AI 报告、设备绑定/解绑与在线电量、用药提醒、留言墙、紧急联系人和语音陪伴三级降级。

### 5.2 量化结果

| 指标 | 实际结果 |
|---|---:|
| 小程序页面 | 18 页 |
| 后端接口 | 39 个业务接口 + 2 个运维端点 |
| JSON 数据集合 | 13 个 |
| smoke | 122/122，通过且连续两遍稳定 |
| 单元测试 | 28/28 |
| WXML 结构校验 | 19/19 |
| 演示态 | 健康 8 条、告警 4 条、预约记录（含待处理/已完成）、报告 1 份、设备电量 66 |

### 5.3 适老化与复现

主体文字保持 36rpx，特大档 44rpx；正文行距 1.7；主要按钮和输入区达到 112rpx；关键文字对比度达到至少 4.5:1；颜色不作为唯一状态手段。`demo:reset` 可恢复健康、告警、提醒、留言、联系人和设备等演示数据，随后按“重置→smoke→单元测试→结构校验”流程回归。

## 六、当前局限与后续规划

### 已完成且验证

核心监护闭环、规则预警、告警留痕、设备与关系治理、AI 对话降级、适老化体系和质量保障体系均已完成演示验证。

### 未实现或待完善

- 预约目前为创建与列表，取消、改期、完成等状态流转未实现。
- 真实语音通话（TRTC）未实现，当前为打字聊天和语音包降级；接入需类目资质。
- 老人端设计稿中的底部 4-tab 尚未还原，当前为双 tab 方案。
- 全局请求失败降级页未实现，当前使用 toast 与页内空态。
- Batch 10 数据级鉴权尚未接入，Mock 模式放行，虽有 token 中间件基础。
- 尚未迁移微信云开发；`sessions.json` 保留期清理也未实现。

### 上线前必须完成

1. 填入真实 `AppSecret` 并完成真实登录真机验证。
2. 接入数据级鉴权，验证不同关系下的越权拒绝。
3. 申请微信订阅消息模板并完成内容安全审核接入。
4. 完成隐私合规审查、数据留存策略和第三方服务授权核验。

### 关键风险与应对

讯飞 Spark 授权状态需在控制台核对；真实音视频能力受 TRTC 类目资质约束；健康报告和提醒必须持续把控医疗合规边界。应对方式是保留本地降级、适配器和免责声明，在真实供应商、资质和真机回归完成前维持演示模式。

## 七、研发管理小结

项目采用目标驱动的分批次迭代，每批次执行“实现→自检→回归→记录”。质量门禁要求 smoke 至少连续两遍通过，并完成语法、结构和关键审计后再合入。研发日志、批次报告、检查清单和演示重置脚本构成完整过程资产，可追溯到具体问题、修复和验证结果。

总体而言，本项目的研发特点是：小步快跑、验证前置、质量内建，在有限 MVP 条件下优先把安全告警闭环和适老化体验做成可复现、可审计的工程结果。
