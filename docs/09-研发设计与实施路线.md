# “桑榆智伴”首版研发方案：微信小程序、后端与设备/机器人接入层

## 摘要：首版成败取决于可信闭环，而非功能数量

首版应定位为“**家属协同照护 + 老人自助照护 + 可信健康事件闭环**”平台，而不是在线诊断或机器人控制系统。建议采用双小程序端（家属端、适老化老人端）、统一 BFF/后端、设备接入网关、规则与 AI 服务、运营管理台的五层架构，围绕“设备数据 → 规则判定 → 告警分发 → 家属/服务方响应 → 处置留痕 → 复盘优化”形成可审计闭环。

P0 的核心交付是：身份与授权、监护关系、设备绑定、心率等时序健康数据、SOS、告警处理、远程语音监护、三类服务预约和医疗免责。按本方案假设，P0/P1/P2 共约 20 周、47 人月；其中 P0 为 8 周、20 人月。该数值是基于团队能力、功能和质量范围得出的**建议估算**，不代表已确认的商务报价或上线承诺。

医疗复诊、处方、诊疗结论必须由取得相应资质并合规接入的医疗机构、医生及其系统承担。桑榆智伴只负责预约导流、病历资料上传、就诊状态回传和服务记录，严禁由 AI 替代医生诊断或开具处方[2]。健康医疗数据属于高敏感数据；微信小程序应遵循隐私保护指引，实行最小必要收集、按功能申请授权，并落实明示同意和用途约束[1]。

对于尚未确认的机器人型号、设备协议、医院 HIS、社区工单系统和支付能力，首版应统一采用可替换的 Mock/仿真适配器。这样可以先冻结产品、数据、权限、告警和验收标准，再根据签约与联调结果替换具体实现，避免外部不确定性倒灌为核心系统风险。

> 本文件为研发方案。用户提到的商业计划书仅作为背景和功能参考；文中尚未取得设备/医院接口规格的部分均显式标注为“待确认/Mock”。截至研究时点，检索到“智伴桑榆——AI赋能的银龄‘心晴’守护者”相关项目信息，但现有材料不足以确认其与本产品存在关联，因此不将该项目资料作为需求或技术事实依据。

## 1. 首版应交付可验收闭环，并以仿真隔离外部不确定性

**首版的目标不是覆盖所有养老场景，而是证明一条高价值、可验收、可追责的照护闭环。** 本方案面向桑榆智伴首版：用户打开小程序后选择“我是家属/我是老人”，老人端以适老化交互为中心，家属端以监护协同和服务调度为中心；后端统一处理身份、设备、健康数据、告警、预约和审计，设备/机器人接入层负责连接真实硬件或仿真设备。

这里所称“机器人”，是具备语音交互、移动/视频陪伴、环境感知或健康监测能力的终端，不应预先等同于某一品牌或医疗仪器。现有材料没有提供其型号、SDK、通信协议、云端账号体系和认证方式，因此相关能力一律按待确认处理。

### 1.1 首版 MVP 的边界

MVP 包含一条主闭环和两条辅助链路：

- **主闭环：** 绑定设备 → 采集心率等健康数据 → 生成健康报告 → 触发预警 → 处理 SOS。
- **服务链路 A：** 预约社区医护、志愿者陪伴或医疗机构复诊。
- **服务链路 B：** 通过机器人开展远程语音监护、一键求助和状态反馈。

由此形成的最小功能集包括：

- 角色登录与监护关系授权；
- 机器人扫码绑定；
- 心率等健康数据查看；
- 预警接收与处理；
- 远程语音监护；
- 一键求助；
- 社区医护、志愿者陪伴和医疗机构复诊预约；
- AI 健康报告与个性化康养建议；
- 适老化老人端基础体验。

### 1.2 核心假设

1. 小程序使用微信开放能力完成登录、消息和隐私流程；具体类目、模板消息/订阅消息能力以微信公众平台审核结果为准。
2. 用户包括老人、家属、社区医护/志愿者（P1）、运营人员和系统管理员；医生诊疗仅在合规第三方医疗机构页面或系统内发生。
3. 首版覆盖单城市、受邀试点，并支持按租户隔离社区/服务商。多城市、多机构大规模接入属于 P2。
4. 设备数据以心率、步数、睡眠、血氧等“健康/生活辅助信号”为范围。若接入血压、血糖、心电、诊断结论或治疗建议，应按医疗器械、数据来源和适用法规另行评估，不能因设备能够输出数据就默认可用于医疗决策。
5. 项目默认自建账户体系，并与微信 OpenID/手机号能力映射。若采用医院实名就诊，应通过独立合规方案接入，且不得将医院账号能力私自用于无关营销。
6. 报警阈值首版使用可配置的“老人/场景规则”，并允许医护或运营人员审核。AI 风险标签只能是辅助特征，不能替代医疗判断。
7. 机器人、语音、医院 HIS、社区工单、支付和地图服务商在签约前均采用 Mock/仿真适配器。只有接口契约、鉴权和端到端测试通过后，才允许切换至真实供应商。

### 1.3 非目标

首版不构建：

- 独立的即时通讯基础设施；
- 自有在线诊疗；
- AI 自动诊断或自动处方；
- 药品配送；
- 医疗器械控制；
- 完整医保结算；
- 面向公众的 UGC 社区；
- 无限制第三方应用市场。

这些边界不是降低产品价值，而是防止首版同时承担身份、设备、医疗、支付和社会化等多重高风险责任。待核心闭环稳定后，再通过明确合同、资质和接口规格逐步扩展。

## 2. P0 必须先形成“数据—告警—处置—留痕”闭环

**首版范围的取舍标准，应是能否验证照护闭环和安全责任链，而不是页面数量或 AI 能力丰富度。** P0 聚焦身份授权、设备接入、事件响应、服务预约和基础运营；P1 提升可信度、运营效率和 AI 可用性；P2 才扩展多社区、开放生态和第三方系统。

| P0 | AI 健康报告、康养建议、免责与引用 | 报告标注时间、数据范围、非诊断及生成标识 | 必须 |
| P0 | 隐私、安全、审计、降级、监控、灰度 | 隐私告知、最小权限、审计日志、故障演练通过 | 必须 |
| P1 | 多设备规则、趋势洞察、家庭协作、运营配置 | 规则版本化；多人协同接警无丢失 | 建议 |
| P1 | 服务方 App/Web、工单、评价、排班仿真 | 服务人员仅看授权任务；工单状态完整 | 建议 |
| P1 | 健康报告解释、知识库、反馈、人工复核 | 建议可溯源；负面反馈进入复核队列 | 建议 |
| P2 | 真实医院 HIS/互联网医院、支付、医保 | 仅在签署协议并完成合规评估后启用 | 可选 |
| P2 | 多社区、服务商市场、开放 API、机器人技能 | 租户隔离、配额、OAuth、SLA 可用 | 可选 |

**告警闭环是首版唯一不可替代的产品价值。** 如果数据只能展示、预警只能推送，而不能确认“谁在何时以何种依据处理、事件最终如何关闭”，系统就只是信息面板，无法承担照护协同责任。

相反，心率采集算法优化、复杂趋势预测和机器人复杂技能即使延后，也不会阻断 MVP 验收。因此 P0 必须确保：

- 预警生成规则可配置；
- 家属和服务方可接单、转派、标记误报或升级；
- 升级路径覆盖无人响应、重复告警和紧急 SOS；
- 每次状态迁移都记录操作人、时间和证据；
- 系统明确显示数据缺失、设备离线和规则未命中。

**第三方能力应全部经过适配器隔离。** 机器人厂商 SDK、社区工单、医院预约、支付、地图、短信/电话和 LLM 都应定义为接口，而不是直接耦合在业务代码中。切换时只改变底层适配器，业务规则、权限和审计逻辑保持不变。

## 3. 数据访问必须遵循“授权优先、分域隔离、全程可撤回”

**老人不是单纯的数据主体，而是数据访问体系中的第一决策人。** 家属可见范围不能由产品默认全量开放，而必须由老人授权、关系级别、数据类别和紧急状态共同决定。否则，监护便利可能直接演变为不必要的家庭监视。

| 角色 | 核心目标 | 可见/可执行范围 | 禁止事项 |
|---|---|---|---|
| 老人（主键持有人） | 自助使用、求助、授权、查看自身数据 | 自身健康、设备、预约、报告；同意/撤回授权 | 查看其他用户；修改诊疗结论 |
| 家属（监护人/成员） | 协同监护、响应告警、代办服务 | 被授权老人的基本信息、设备、告警、报告、预约；远程语音需许可 | 未授权访问；导出原始音频；转授权 |
| 社区医护/志愿者 | 履约服务 | 仅服务工单、任务地点、必要健康摘要、紧急联系信息 | 查看无关病历；使用数据进行二次营销 |
| 医疗机构/医生 | 互联网诊疗（第三方承担） | 由医疗机构系统按复诊规则和医师要求处理 | 由本平台生成诊断/处方 |
| 运营/管理员 | 配置、审核、排障 | 按管理员角色分权；生产数据脱敏或审批后访问 | 批量导出明文敏感数据；绕过审计 |

**权限模型采用“关系 + 用途 + 数据类别 + 紧急状态”。** 推荐采用 RBAC 管理后台功能权限，采用 ABAC/策略管理动态数据权限。核心判断条件包括：

- 监护关系是否有效；
- 授权是否处于有效期；
- 数据类别是否属于当前用途；
- 是否处于紧急状态；
- 紧急操作是否留有后续确认和审计证据。

例如，家属默认可查看“健康摘要、活跃告警、设备状态”，但原始音频、精确轨迹和完整病历摘要应单独授权。SOS 触发后可临时提升紧急联系人权限，但必须在事后展示“临时访问记录”，并允许老人确认或申诉。

**授权必须可撤回，且撤回结果必须真正生效。** 每个授权记录应包含授权人、受托人、关系证明或确认方式、范围、有效期、撤回时间及版本。撤回后，后端应立即使相关 access token/session cache 失效，并阻止后续数据拉取；但出于审计要求保留的必要记录，应加密归档，不能被普通业务查询直接返回。

微信小程序的数据收集应遵循隐私保护指引：仅处理实现功能所必需的信息，按用途声明，并在用途或范围变化前再次取得明示同意；共享或转让至第三方时，应取得单独同意[1]。因此，首版不能因“家庭监护”而默认要求身份证、精确轨迹或通讯录；这些字段必须在真实业务触发时分级收集。

## 4. 用户体验应围绕关键任务简化，而不是双端简单镜像

**首版只需固化少量高价值流程，复杂设置应后置。** 用户流程应保证老人能快速进入核心操作，家属能完成响应和服务调度，系统则对每一步形成可追踪记录。

### 4.1 老人端：三步内完成关键操作

1. 打开小程序 → 选择“我是老人” → 手机号/微信授权（仅收集必要账号标识）。
2. 引导完成基本信息（昵称、出生年月可选）、紧急联系人、语音授权与隐私确认；不要求一次填写完整病历。
3. 首页仅保留“一键求助”“语音呼叫家属”“我的健康”“我的服务”；大按钮、语音播报、顶部状态条。
4. 按下 SOS 后，自动进入“已发出求助”倒计时页面，持续显示呼叫状态、已通知对象和取消确认，避免老人重复按压。
5. 告警或报告到达时，采用“重要一条”优先展示，不用红点堆叠；老人可听、可看、可确认。

### 4.2 家属端：围绕异常、求助和代办形成响应闭环

1. 选择“我是家属” → 登录 → 输入老人邀请码或扫码建立关系 → 老人确认。
2. 首页展示“风险等级/最新健康摘要、活跃告警、设备在线、今日服务”。
3. 点击告警后，依次执行：查看证据 → 联系老人/机器人语音 → 自行接单、转社区或标记为误报 → 填写处置结论。
4. 在服务页选择“社区医护、志愿者陪伴、医疗机构复诊”：前两类创建平台工单；复诊类进入合作医疗机构/医院预约流程或展示其合法入口。
5. AI 报告页支持“查看数据来源、采纳建议、咨询医生/社区”，但不提供“立即买药/自行治疗”的引导。

### 4.3 关键用户旅程

| 旅程 | 前端动作 | 后端/接入层动作 | 成功判据 |
|---|---|---|---|
| 绑定机器人 | 扫码/输入设备码 → 授权 → 命名 | 校验设备证书、建立 device_elder 关系、下发配置 | 老人/家属可见设备在线和历史命令 |
| 心率异常 | 设备上报 → 老人端轻提示 | 写入时序库、规则引擎评估、告警去重 | 告警页面、通知和审计记录一致 |
| SOS | 长按/单击确认 → 呼叫中页 | 创建最高优先级事件、并行通知家属/服务方/可选电话 | 5分钟内至少一次确认或升级 |
| 远程语音 | 家属申请 → 老人许可 → 双向/单向模式 | WebRTC/厂商通道、许可票据、录音策略 | 未获许可不可建立媒体流 |
| 复诊预约 | 选机构/科室 → 上传既有病历资料（可选） | 创建预约意向；跳转/回调合规机构 | 本端不生成诊疗结论；状态可回写 |

## 5. 五层架构应通过接口边界控制复杂度，而非提前过度微服务化

**首版应采用逻辑分层、物理适度的部署结构，先保证数据流和责任边界清晰，再按负载拆分服务。** 过早拆分为大量独立服务会增加运维、鉴权和一致性成本；但若把所有能力写入单体，又会把设备、医疗和 AI 风险混在一起。

```text
老人/家属小程序 → CDN/WAF → API网关（鉴权、限流、路由）
                      ├─ 用户/关系/授权服务
                      ├─ 设备接入网关（MQTT/HTTPS/WebSocket；Mock+真实适配器）
                      ├─ 健康数据服务（原始、清洗、聚合）
                      ├─ 告警/规则/事件服务（状态机、升级、SLA）
                      ├─ 预约/工单服务（社区/志愿者/复诊适配器）
                      ├─ 语音/媒体服务（信令、许可、录制、审计）
                      ├─ AI 服务（报告/建议/安全过滤；模型网关）
                      └─ 运营/审计/配置服务
                ↓
      关系型DB / 时序DB / 对象存储 / 缓存 / 消息队列 / 日志追踪
```

建议采用“**小程序原生/TypeScript + 组件化**”实现双端，并通过共享设计令牌和权限指令控制差异；后端可采用“**Java 17 + Spring Boot / Go**”二选一。团队若偏业务系统且重视企业生态，可优先选择 Spring；若设备接入和实时推送占主导，可优先选择 Go。两者均须遵循统一 OpenAPI、领域模型和审计规范。

| 层 | 建议技术 | 关键职责 | 重要约束 |
|---|---|---|---|
| 小程序 | 微信小程序原生、TypeScript、状态管理、Canvas/echarts-for-wechat | 双端 UI、无障碍、离线提示 | 按平台规则申请权限；不缓存未授权敏感数据 |
| BFF/API | Node/Java/Go；OpenAPI、版本化 REST；必要时 GraphQL | 聚合、鉴权、裁剪、错误码 | 不做医疗/AI决策；只转译 |
| 设备网关 | MQTT Broker 或 HTTPS Ingress、WebSocket、规则引擎 | 设备认证、上行校验、下行命令、QoS | 每条消息带 deviceId、timestamp、schema 版本 |
| 数据存储 | PostgreSQL/MySQL、TimescaleDB/InfluxDB、Redis、OSS | 业务、时序、缓存、媒体 | 健康数据冷热分离；备份、加密、保留期策略 |
| 消息/任务 | Kafka/RabbitMQ、延迟队列 | 数据入库、告警、通知、报告生成 | 幂等、重试、死信、背压 |
| AI | 模型网关、RAG/知识库、内容安全 | 报告草稿、建议、异常摘要 | 非诊断；提示注入防护；记录模型/版本/输入摘要 |
| 运维安全 | K8s/Serverless、Prometheus、Grafana、ELK/OTel、密钥管理 | CI/CD、灰度、审计、应急 | 最小权限、网络隔离、定期演练 |

**实时性要求应按风险等级拆分，而不是所有数据都追求“秒级”。** 普通健康趋势可采用批量或准实时写入；告警和 SOS 采用独立高优先级通道。机器人语音信令、告警事件和时序指标应使用不同队列与降级策略，避免普通指标写入积压时阻塞紧急事件。

## 6. 适老化不是放大字体，而是降低认知、操作和失败成本

**适老化应覆盖信息架构、反馈、容错、媒体控制和失败恢复，不能止于视觉样式。** 如果关键操作仍需多级菜单、授权结果不清楚、网络失败无法恢复，即使字体较大，也不构成可用设计。

建议老人端基础字号不小于 18px，主标题 22px，关键按钮高度不小于 56×56 有效区域，并支持至 200% 文字缩放。文本与背景对比度应满足 WCAG 2.1 相关要求；WCAG 2.1 是可供设计、开发和采购使用的可测试建议，并非中国养老软件的强制法律门槛[4]。

| 规范 | 老人端规则 | 家属端规则 |
|---|---|---|
| 信息架构 | 底部 4 个标签：首页、健康、服务、我的 | 首页、老人、告警、服务、我的 |
| 主按钮 | 红/橙 SOS 固定可见；不在滚动区外 | 告警卡片内嵌接单/转派 |
| 交互 | 单击优先；禁用长按快捷操作；二次确认破坏性操作 | 支持筛选、批量、工单备注 |
| 语音 | 关键页有“朗读”和“语音指令”开关；每次录音前明示 | 语音监护先申请许可，实时显示麦克风状态 |
| 错误 | “没联网”必须显示重试和客服/紧急电话，不显示技术栈错误码 | 错误码仅展示复制入口供客服排查 |
| 无障碍 | 支持大字号、深色高对比、屏幕阅读顺序；视频不自动播放声音 | 运营图表支持文字摘要 |
| 防误触 | SOS 采用“按下 1 秒 + 松开确认”，避免单次误按 | 紧急联系优先电话/短信，平台消息作为补充 |

**任何需要授权的能力，都应先解释用途，再在真实触发时申请。** 微信隐私规范强调按功能收集、明示目的和用途约束[1]。因此，进入老人端首页不应一次性索取麦克风、位置、通讯录和相册；这些权限应在语音监护、服务地址或头像上传等具体操作触发时申请。

权限被拒后，系统应保留基本功能，并明确展示替代路径，而不是进入无限循环。对于 SOS 和紧急联系等涉及人身安全的流程，应区分“产品功能授权”和“生命安全应急”：不能因用户拒绝非必要权限而阻断核心求助，但临时升级访问仍须形成记录。

## 7. 数据模型必须同时支持原始证据、业务解释和责任追踪

**健康数据的价值不在于单点数值，而在于来源、质量、授权和处置过程能否被还原。** 因此，系统应保存原始观测、清洗结果、规则版本、告警状态和响应记录，不能只保留一个最终“风险结论”。

`health_observation` 的 `data_category` 至少包括：heart_rate、steps、sleep、spo2、blood_pressure、temperature、device_status、manual。原始值与清洗/展示值应分开保存；只有经过质量规则验证的数据，才能用于告警和报告。

```text
User(id, role, phone, wechat_open_id, consent_version, created_at)
ElderProfile(id, user_id, display_name, birth_date, emergency_contact_encrypted, preferred_language, accessibility_settings)
CareRelationship(id, elder_id, family_user_id, role, scope, valid_from, valid_to, status, evidence_ref)
Device(id, device_type, vendor, model, firmware, device_secret_ref, status, bound_elder_id, pairing_code)
DeviceCommand(id, device_id, command, payload, idempotency_key, status, result, created_at, delivered_at)
HealthObservation(id, elder_id, device_id, data_category, observed_at, value_json, unit, source_type, quality_status, schema_version)
Report(id, elder_id, period_start, period_end, summary, advice_refs, data_quality, disclaimer, model_id, created_at)
AlertRule(id, tenant_id, name, trigger_expression, severity, channels, escalation_policy, version, enabled)
AlertEvent(id, rule_id, elder_id, device_id, severity, state, evidence_snapshot, first_at, last_at, sla_due_at)
AlertResponse(id, event_id, actor_id, action, note_encrypted, created_at)
Appointment(id, elder_id, service_type, provider_ref, slot_ref, status, reason, attachments, consent_ref, external_id)
ServiceProvider(id, type, name, region, adapter_type, credentials_ref, sla_config)
VoiceSession(id, elder_id, family_id, mode, consent_id, start_at, end_at, recording_policy, audit_ref)
ConsentRecord(id, user_id, category, purpose, scope, method, version, agreed_at, withdrawn_at)
AuditLog(id, actor_id, subject_id, action, result, request_id, ip, user_agent, before_ref, after_ref, created_at)
```

| 数据域 | API 示例 | 方法/路径 | 权限与说明 |
|---|---|---|---|
| 认证/关系 | 创建监护关系 | POST /v1/elders/{id}/relationships | 需老人确认；返回授权范围 |
| 设备 | 绑定/解绑/命令 | POST/DELETE /v1/devices/{id}/bind、POST /v1/devices/{id}/commands | 设备证书；命令幂等 |
| 健康 | 上报/查询/聚合 | POST /v1/health/observations、GET /v1/elders/{id}/health/summary | 范围授权；时区、分页、质量标志 |
| 告警 | 查询/响应/升级 | GET /v1/alerts、POST /v1/alerts/{id}/responses | 状态机校验；家属/服务方分权 |
| 语音 | 申请/许可/结束 | POST /v1/voice/sessions、POST /v1/voice/sessions/{id}/consent | 许可票据；不长期缓存媒体 |
| 预约 | 创建/取消/回写 | POST /v1/appointments、PATCH /v1/appointments/{id} | service_type 校验；external_id 幂等 |
| 报告 | 生成/查询 | POST /v1/reports、GET /v1/reports/{id} | 报告含 disclaimer、来源引用 |
| 管理 | 规则/服务商/审计 | GET/PATCH /v1/admin/alert-rules | 管理员 MFA；配置变更审计 |

**API 设计应把“事实、判定、处置”分开。** `HealthObservation` 记录事实；`AlertEvent` 记录规则判定；`AlertResponse` 记录人为处置。三者通过不可变引用关联，可以追溯“数据为何异常、规则如何触发、谁如何处理”。报告同样应保存 `data_quality`、模型版本、时间范围和免责声明，避免将局部或低质量数据包装成确定性结论。

## 8. 告警系统必须依靠状态机、升级策略和证据快照保证不丢事件

**告警系统的核心不是“发通知”，而是确保每个事件都有明确责任人、截止时间、升级路径和关闭依据。** 如果多个用户同时接单、重复通知或跨端状态不一致，系统即使生成告警，也无法形成可靠协同。

建议状态包括：

`open → acknowledged → in_progress → resolved`

或：

`open → escalated → external_dispatched → resolved`

中间允许 `false_positive`、`cancelled`、`needs_human_review`。每次迁移必须包含 `actor、reason、channel、evidence_ref、occurred_at`。设备重复上报不创建无限事件，而应通过 `fingerprint + severity + time window` 进行去重，同时更新 `last_at`。

```text
open --家属/服务方接单--> acknowledged
acknowledged --开始处置--> in_progress
in_progress --处置完成/风险解除--> resolved
open/acknowledged --SLA到期或无响应--> escalated
escalated --呼叫社区/120/紧急联系人--> external_dispatched
任何非终态 --证据表明无需处置--> false_positive
resolved/false_positive --发现复发/错误--> reopen(→ open)
```

| 状态 | 允许动作 | 不可变规则 |
|---|---|---|
| open | acknowledge、escalate、close | 必须关联告警规则和数据证据 |
| acknowledged | assign、add_note、start | 只能由授权人或系统升级操作 |
| in_progress | dispatch、contact_elder、resolve | 不得删除原始告警 |
| escalated | external_dispatch、reassign | 必须记录通知送达/失败 |
| resolved | reopen（限定期限） | 必须填写处置结论与证据 |
| false_positive | review、suppress_rule（审批） | 不得静默丢弃；进入规则复盘 |

**升级策略应保守，但不能让平台承担超出能力的处置责任。** P0 默认策略如下：

| 场景 | 建议 SLA |
|---|---:|
| SOS | 1 分钟尝试联系家属，5 分钟未确认则升级 |
| 高风险心率规则 | 5 分钟确认，15 分钟升级 |
| 设备离线 | 先提示，30 分钟仍未恢复则生成运维/家属提示 |
| 重复告警 | 短时间内重复 3 次后合并并升级 |

上述数值是产品建议，正式上线前必须由试点社区、老人及其家属在服务协议和风险预案中确认。若已明确需要急救，小程序只能提供“拨打 120/紧急联系人”的便捷入口和位置辅助，不能承诺平台能够替代急救调度。

**告警通道必须多路冗余。** 微信订阅消息、App/小程序内推送、短信、电话机器人等通道可以采用适配器组合，但每次投递必须记录 `request_id、channel、status、cost、latency`。应持续监控“已发送但无确认”“家属离线”“机器人不可用”等情形，并在老人端显示“通知可能未送达”，而不是用成功发送掩盖实际接收失败。

## 9. 设备、语音和第三方预约都应通过契约隔离，真实能力延迟绑定

**接入层的核心价值是把未知硬件和外部系统转化为稳定内部契约。** 真实设备、医院系统和社区工单在签约前不可假设可用；首版应优先冻结接口、仿真数据、失败模式和验收标准。

### 9.1 设备与机器人接入

设备与机器人接入层采用“**设备适配层 + 设备影子 + 命令总线**”：

1. 机器人通过扫码或设备码发起绑定，由后端验证证书或配对码，并建立 `device_elder` 关系。
2. 设备上行数据写入原始 topic，经 schema 校验、去重和质量控制后入库。
3. 后端更新设备影子，并对外提供统一查询和状态机。
4. 下行命令经过 idempotency key、有效期、权限和回执校验，避免重复操作。

具体机器人型号、SDK、音视频协议、云端账号体系和 OTA 方式尚未确认，因此 P0 只承诺“**符合已签署设备规范的设备可接入**”，不承诺自动兼容任意机器人。

| 能力 | P0 契约 | 外部不可确认时的 Mock | 真实接入验收 |
|---|---|---|---|
| 心率等健康数据 | observation schema、时区、单位、质量状态 | 可配置轨迹生成器，覆盖正常、突变、缺失 | 连续 24 小时数据一致性；断网恢复 |
| 设备状态 | online/offline/low_battery/error | 随机故障注入 | 状态切换、告警和命令回执验收 |
| 语音监护 | session、mode、consent、start/stop | WebRTC 本地回环或假信令 | 延迟、丢包、权限、录制开关 |
| 命令控制 | command、idempotency、timeout、result | 内存队列返回 success/failure | 并发、重试、越权和设备离线场景 |

### 9.2 语音监护边界

语音监护支持单向监听和双向通话两种模式。单向模式只能在老人明确授权、界面持续提示且授权可撤回的条件下启用，不能默认开启。双向模式采用标准 WebRTC 或厂商 SDK，会话票据绑定双方身份、老人许可和有效期。

音频不得用于训练、营销或无授权转写。需要录音时，应满足当地法律和平台规则，并在会话前后提示。所有会话至少记录：

- 许可记录；
- 开始和结束时间；
- 加密存储位置；
- 访问日志；
- 保留和删除策略。

### 9.3 预约与外部系统边界

预约服务必须拆分三种类型，不能用一套“服务订单”逻辑掩盖责任差异：

1. **社区医护**：由桑榆智伴自身运营或合作的社区服务承接，可以包含预约、派单、履约和评价。
2. **志愿者陪伴**：由社区或运营团队承担招募、审核、培训、保险和排班，平台只负责服务撮合。
3. **医疗机构复诊**：互联网诊疗受医疗机构和医师责任约束。国家卫健委政策解读明确，互联网诊疗监管要求覆盖实名制就诊、接诊与终止条件、电子病历管理、数据保存等；病历、处方等关键信息的流转应可追溯[2]。

因此，平台可以：

- 展示可选合规机构；
- 上传既有病历资料；
- 预约/改约；
- 接收就诊状态；
- 保存非诊疗服务记录。

平台不得：

- 自行诊断；
- 自动开具处方；
- 用 AI 替代医生；
- 在无资质情况下保存或展示处方。

AI 健康建议只能使用“关注、记录、就医咨询”等低风险表达。涉及急性症状、跌倒、持续胸痛、意识异常等高风险情况，必须提示紧急求助，并建议联系急救或线下医疗。

**第三方预约适配器应统一采用“能力发现—授权—预约意向—幂等回写—异常补偿”流程。** P1 前只实现本地 FakeProvider，返回固定机构、时段和状态；签约后按机构提供的 API、HIS 或人工 Excel/工单流程替换。接口应明确：

- `provider_ref`；
- `external_id`；
- `slot_ref`；
- `consent_ref`；
- `cancellation_policy`；
- `webhook_signature`；
- 重试与对账机制。

任何机构未提供明确接口规格时，不得写入代码，只能通过配置化适配器对接。

## 10. 安全、隐私和医疗免责必须进入产品代码，而不能停留在说明文档

**健康养老系统不能依赖文档声明安全，而必须把最小化、可撤回、可审计和医疗边界转化为工程控制。** 隐私政策、角色权限、加密、日志和免责声明应共同构成责任链。

微信小程序隐私保护指引要求开发者只处理实现功能所必需的信息，并在用途或范围变化前再次取得明示同意[1]。健康医疗数据安全指南 GB/T 39725-2020 为现行推荐性国家标准，于 2020 年 12 月 14 日发布、2021 年 7 月 1 日实施，可为健康医疗数据安全控制提供参考[3]。

### 10.1 安全控制要求

- **数据最小化：** 默认收集手机号/OpenID；病历资料仅在复诊预约时上传；精确轨迹默认不采集。
- **加密：** 传输使用 TLS；存储对 PII、健康数据、录音引用和紧急联系信息加密；密钥由 KMS 管理并定期轮换；备份同样加密。
- **访问控制：** 服务间 mTLS/Token；管理员 MFA；生产访问采用审批、临时凭证和会话录制。
- **审计：** 认证、授权、关系变更、设备绑定、告警处理、报告生成、导出、录音访问、管理员操作均进入不可篡改日志。
- **留存与删除：** 在隐私政策中明示类别、目的、保存期限、第三方和权利联系方式；支持注销、删除及匿名化导出。法定留存数据应隔离保存。
- **漏洞与应急：** 实施 SCA/SAST/DAST、依赖 SBOM、渗透测试、灾备演练和事件通报流程。

### 10.2 医疗免责声明

报告页、告警详情和服务页应在对应上下文持续展示以下提示：

> 本功能提供健康信息记录、风险提示与康养参考，不构成诊断、治疗、急救或用药建议；如有不适或紧急情况，请及时联系医疗机构或急救服务。

若报告由生成式 AI 生成，还应：

- 标识“AI 生成”；
- 显示模型、版本或提供商信息（如适用）；
- 保留人工复核入口；
- 提示内容可能存在错误。

生成式 AI 服务管理办法要求提供者尊重个人信息权益，提高生成内容准确性与可靠性，并建立投诉举报机制[5]。因此，P1 报告功能应记录：

- prompt/上下文摘要；
- 模型版本；
- 输入来源引用；
- 生成时间；
- 人工复核或用户反馈。

### 10.3 关键合规检查清单

| 项目 | P0 动作 | 上线门槛 |
|---|---|---|
| 隐私政策/指引 | 字段—目的—第三方—保存期映射；逐功能授权 | 法务、安全、产品联合签字 |
| 监护授权 | 老人确认、范围、撤回、审计 | 所有家属请求均通过授权校验 |
| 健康数据 | 分级、加密、导出限制、备份恢复 | 渗透测试和数据恢复演练通过 |
| 远程语音/录音 | 许可、通知、保留期、访问审批 | 无许可无法建立媒体流 |
| AI 报告 | 非诊断标识、引用、反馈、人工复核 | 不能输出处方或确诊结论 |
| 复诊导流 | 第三方资质/协议、跳转白名单、病历最小化 | 明确医疗机构承担诊疗责任 |

## 11. P0 应先验证闭环，P1 提升可信运营，P2 再扩展生态

**20 周、47 人月是目标条件下的范围估算，不是承诺。** 团队配置、并行程度、真实设备联调周期和第三方签约进度都会改变实际投入。若人员不足或外部依赖延迟，应优先砍掉 P1/P2，保留 P0 闭环，而不是以完整功能名单换取不可验收版本。

按 5 人核心团队估算，P0 约 4 个月；按 8–10 人并行实施，可压缩至约 8 周。图 2 采用“周数”和“人月”双口径，目的在于区分日历时间和资源投入，不能将两者简单等同。

| 阶段 | 周次 | 主要任务 | 退出条件 |
|---|---:|---|---|
| P0-1 设计与骨架 | 1–2 | PRD/交互冻结、数据模型、API、Mock、CI、权限、隐私文本 | API契约/权限矩阵/告警状态机评审通过 |
| P0-2 双端与设备闭环 | 3–5 | 角色登录、绑定、数据看板、SOS、告警、语音许可、Mock机器人 | 老人/家属核心路径 E2E 通过 |
| P0-3 服务与报告 MVP | 6–7 | 三类预约、工单、报告草稿、免责、审计 | 第三方仅 Mock；预约状态可回写 |
| P0-4 安全与试点上线 | 8 | 安全测试、灰度、监控、演练、培训 | 高风险缺陷清零，运行手册完成 |
| P1-1 可信扩展 | 9–11 | 真实设备试点、规则版本、服务运营台、报告解释 | 至少一种真实设备通过验收 |
| P1-2 AI与运营 | 12–14 | RAG知识库、反馈闭环、人工复核、KPI看板 | 报告引用/免责/人工升级可用 |
| P2-1 生态准备 | 15–17 | 多社区租户、服务商接入、OAuth、开放API | 租户隔离与配额测试通过 |
| P2-2 真实医疗对接 | 18–20 | 合规医院/支付/工单适配器 | 协议、资质、接口、审计逐项验收 |

P0 研发任务可拆分为：

- 产品/设计：角色流程、适老化设计规范、内容/免责；
- 前端：双端脚手架、老人首页/SOS、家属告警、设备/健康/服务页；
- 后端：身份关系、设备网关、时序数据、规则告警、预约、审计；
- AI：报告模板、知识引用、内容安全、人工复核；
- 测试：契约测试、设备故障注入、权限/越权、无障碍、压测；
- 运维/安全：基础设施即代码、密钥、日志、灰度、备份。

**任务验收应以可观察行为为单位，而不是以页面或接口数量为单位。** 每个用户故事至少覆盖：

- 正常路径；
- 权限拒绝；
- 设备离线；
- 重复提交；
- 数据缺失；
- 取消或撤回；
- 异常恢复。

例如，“家属处理心率告警”不能只验证页面展示，还必须验证越权访问、重复接单、SLA 升级、通知失败和服务端审计。

## 12. 上线门槛应是安全闭环可证明，而不是功能全部完成

**首版上线应采用“安全准入 + 灰度试点”，先验证高风险链路，再扩大用户范围。** 如果告警、授权、语音或数据审计未通过验收，即使页面完整，也不应进入真实老人环境。

CI 流水线应包括：

1. Lint/类型检查；
2. 单元测试；
3. API 契约测试；
4. 依赖漏洞扫描；
5. 构建；
6. 部署预发环境；
7. E2E 测试；
8. 安全测试；
9. 人工验收；
10. 生产灰度；
11. 监控检查；
12. 发布归档。

每次发布必须包含版本、变更说明、数据库迁移、配置变更、回滚方案、告警规则和责任人。

| 测试类型 | 重点 | 通过标准示例 |
|---|---|---|
| 功能 | 双端流程、状态机、预约、报告 | P0 用例 100% 通过；无阻塞缺陷 |
| API契约 | Mock/真实适配器、版本兼容 | 契约差异阻断发布 |
| 权限/安全 | 越权、令牌、撤回、加密、审计 | 渗透测试高风险问题清零 |
| 设备/IoT | 断网、重传、时钟偏差、离线命令 | 数据不丢、不重、不越权 |
| 实时/告警 | SOS、升级、并发接单、通知失败 | SLA 在负载和故障条件下达标 |
| 适老化/无障碍 | 大字号、语音、对比度、误触 | 目标用户可用性测试通过 |
| 混沌/容量 | 消息积压、下游超时、机器人掉线 | 核心告警链路保持可用 |

**上线门槛应明确、可测量、不可谈判：**

- 所有 P0 缺陷已关闭；
- 关键告警链路完成故障演练；
- 权限和隐私评审完成；
- 监控告警覆盖 API 错误率、消息延迟、设备在线率、SLA 超时、通知失败、机器人命令失败、异常登录和报告生成失败；
- 已建立值班、重大事件升级和用户沟通模板。

生产发布采用 5% → 20% → 50% → 100% 的灰度策略，并至少观察 24 小时。真实医院、支付、电话外呼等高风险供应商应在独立适配器标志下切换，支持分钟级回滚。

## 13. KPI 必须衡量闭环质量，而非诱导高频使用

**桑榆智伴的健康度不能只看 DAU，而应看照护闭环是否更快、更准、更安全。** 老人端尤其不应通过红点、连续提醒或紧迫文案诱导高频打开，而应帮助用户在更少操作中确认安全状态。

| 维度 | 指标 | 定义/目标（建议试点值） | 解读边界 |
|---|---|---|---|
| 安全 | SOS 首响时间 | 从触发到首个确认；P0 目标 <5 分钟 | 依赖人员在线率，不作为绝对医疗承诺 |
| 告警 | 告警关闭率、误报率 | 有结论事件/全部事件；按规则复盘 | 不能只追求降低告警数量 |
| 健康 | 有效数据率 | 通过质量校验的观测/全部观测 | 缺失和噪声应可见 |
| 服务 | 预约完成率 | 履约完成/已创建；按服务类型拆分 | 受服务商供给影响 |
| 语音 | 许可遵从率 | 有有效许可的会话/全部会话 | 必须为 100% |
| 适老化 | 关键任务成功率 | 老人独立完成 SOS/查看/呼叫比例 | 用真实用户测试，而非自评 |
| AI | 报告引用率、升级率 | 建议可追溯比例；转人工/就医比例 | 不得用满意度掩盖安全风险 |
| 系统 | API 可用性、告警延迟 | 99.9% 及分位延迟；试点目标 | 需明确区域、网络和供应商排除项 |

**风险登记必须落实到责任人和触发条件，而不是停留在风险名称。**

| 风险 | 影响 | 缓解措施 | 责任人 |
|---|---|---|---|
| 未确认机器人协议 | 接入延期、体验不稳定 | 设备抽象层 + Mock；先开展真实设备 PoC | 硬件负责人 |
| 健康数据误报/漏报 | 信任受损、安全风险 | 多源校验、阈值审批、人工升级、数据质量展示 | 医疗产品/算法 |
| 隐私越权 | 合规处罚、家庭纠纷 | 授权模型、审计、撤回、渗透测试 | DPO/安全 |
| AI 幻觉或越界建议 | 误导用户 | 非诊断护栏、知识引用、人工复核、内容安全 | AI负责人 |
| 第三方医疗/支付接口未开放 | 复诊流程阻塞 | 预约意向 + 人工回写；禁止自行诊疗 | 商务/后端 |
| 老人误触或不会使用 | 紧急流程失败 | 适老化测试、语音反馈、家属备用流程 | UX |
| 通知未送达 | 告警失效 | 多通道、送达回执、离线提示、升级 | 平台负责人 |
| 突发高并发告警 | 系统雪崩 | 队列隔离、限流、降级、压测 | SRE |

这些指标和风险项构成持续运营机制：KPI 用于发现闭环退化，风险登记用于决定优先级，灰度与演练用于验证改进是否有效。若指标改善但真实用户完成率下降，应以可用性测试和行为证据校正，而不是继续优化单一数字。

## 14. AI 提示词应服务可执行交付，并经过来源、版本和审批控制

**AI 适合加速规范、接口、测试和调研，不应直接成为需求真相源或医疗结论来源。** 所有提示词都应绑定角色、约束、输入、输出格式、验收标准和禁止项；医疗、隐私和高风险操作还需经过人工审批。

医疗内容禁止输出诊断、处方、剂量、急救指挥和确定性风险判断。涉及健康数据时，提示词必须要求注明来源、数据范围和不确定性；报告只能形成低风险生活方式或就医咨询建议。

### 14.1 通用使用规则

1. 输入只提供完成任务所需的最小上下文，避免粘贴真实姓名、病历、录音转写、手机号或 token。
2. 每次输出必须标注：用途、版本、依据文件、是否包含生成式内容、待人工复核项。
3. 严禁 AI 自动修改生产代码、生产配置或隐私规则；代码需经过评审和 CI，文档需经产品/法务确认。
4. 需求和 API 生成采用“契约优先”：先确认实体、权限、状态机、失败模式和验收标准，再生成细节。
5. 提示词纳入版本管理，记录模型、版本、输入摘要、输出、评审人和撤回记录。
6. 测试生成必须基于已冻结的需求或接口；发现矛盾时标记“待澄清”，不得自行编造接口。
7. 使用真实用户录音、视频、聊天和病历前，必须完成合法授权和数据脱敏；合成数据仅用于训练或测试时，也应明确标识。
8. 外部资料以权威来源、合同和接口文档为准；检索摘要不得替代合同、法规原文或供应商技术文档。

### 14.2 提示词模板

#### 前端

```text
你是适老化小程序前端架构师。基于本方案的角色、权限矩阵、页面清单与无障碍规范，输出老人端“一键求助”组件的 TypeScript 组件契约、状态、交互步骤、异常文案、单测用例。
约束：主操作不超过两步；按钮最小可点击区域 56×56；必须显示呼叫状态；不得自行采集位置；不得假设设备能力。
输出：Props/Events、状态表、axe/WCAG 检查点、Markdown 表格、5 个边界测试；不确定项列入“待澄清”。
```

#### 后端

```text
你是后端工程师。为 /v1/alerts/{id}/responses 设计 OpenAPI 3.1、状态机守卫、幂等规则、审计字段、错误码、并发与权限测试。
输入：AlertEvent 状态机、家属/服务方权限、SLA 升级策略。
约束：禁止删除原始告警；必须引用 actor、consent、evidence；命令失败必须可补偿。
输出：YAML、状态迁移表、DB 索引建议、SQL 示例、契约测试用例。
```

#### 测试

```text
你是测试架构师。基于“心率异常告警闭环”需求生成分层测试策略：单元、契约、E2E、混沌和隐私。
覆盖：设备断网重传、重复上报、家属和服务方并发接单、授权撤回、通知失败、SLA 升级、数据质量缺失。
输出：测试金字塔、用例表、故障注入清单、可观测断言、退出标准。
```

#### 产品设计

```text
你是银龄产品设计师。为老人端“健康摘要”撰写信息架构、内容优先级和无障碍文案。
约束：默认显示一条最重要的待处理事项；趋势解释用通俗语言；图表必须提供文字替代；关键风险明确“非诊断，必要时就医”。
输出：低保真流程、组件清单、文案表、可用性测试任务。
```

#### AI 健康报告

```text
你是健康报告生成助手。基于已授权、已脱敏的健康观察摘要、老人偏好和经批准的康养知识，生成建议草稿。
约束：必须列出数据时间范围、覆盖缺失、引用来源；使用“可考虑/建议记录/建议咨询医生”；禁止疾病名称确定性判断、用药、急救指令。
输出：JSON（summary、advice[]、evidence[]、disclaimer、confidence）及人工复核清单。
```

### 14.3 示例输出

**用户需求：** 老人心率 118 bpm 持续 10 分钟，老人端和家属端分别如何处理？

**AI 建议回答：**

1. 后端先验证数据来源、质量和重复状态；确认有效后创建或合并告警事件，并附上原始观测引用和设备状态。
2. 老人端只显示可理解的风险提示、安抚引导和“呼叫家属/求助”入口，不自行诊断。
3. 家属端收到通知，可按“联系老人—查看设备—接单/转社区—关闭”处理；超过 SLA 且无响应时升级。
4. 若规则已标记为高风险，或老人同时触发 SOS/跌倒等事件，系统应优先提示紧急联系和线下医疗，不由 AI 决定具体疾病或治疗。
5. 输出必须附带证据快照、规则版本、处理时限和审计记录，确保事件可以复盘。

该示例体现的是闭环设计，而非临床阈值。任何阈值上线前，都应由医学或运营负责人审批，并结合具体设备精度、老人疾病状态和试点规则配置。

## 15. 首版应按“六步法”推进：先冻结契约，再验证真实能力

**研发执行顺序应是先治理、再闭环、后扩展，而不是从页面或 AI 功能入手。** 首版推荐采用以下六步：

1. **Day 0–3：范围治理。** 冻结用户角色、监护授权、数据字典、隐私清单、告警状态机和不做清单。
2. **Day 4–10：架构与 Mock。** 完成 API、设备适配器、时序存储、权限中间件、E2E 骨架和仿真设备；真实硬件未到货时，通过 Mock 推进。
3. **Day 11–30：P0 双端闭环。** 优先交付老人 SOS、家属告警、设备数据、语音许可、服务预约和基础审计。
4. **Day 31–45：安全与试点。** 完成安全测试、适老化可用性测试、灰度、监控和应急；邀请少量家庭与社区开展受控试点。
5. **Day 46–70：P1 可信扩展。** 接入首批真实设备，完善报告、规则、工单和服务运营；根据实际投诉、误报和告警关闭率迭代阈值。
6. **Day 71–140：P2 生态准备。** 仅在资质、合同、接口、数据保护影响评估和验收条件齐备后，对接真实医院、支付、多社区与开放 API。

**决策原则应是“有合同才有接口，有规格才有实现，有演练才有上线”。** 任何新增机器人、医院、支付、语音、短信或 AI 模型，都必须经过：

- 供应商评估；
- 数据/责任边界审查；
- 接口契约定义；
- 密钥与鉴权配置；
- 故障注入；
- 安全测试；
- 业务验收。

未满足条件的能力不得进入生产。该原则会牺牲短期功能数量，但能避免供应商锁定、合规倒灌和事故责任不清。

## 结论：先用可审计的照护闭环验证产品，再扩展 AI 与生态

桑榆智伴首版应把“**可信、适老、可接入、可审计**”置于功能广度之前。老人端以一键求助、语音和大字清晰反馈为中心；家属端以告警响应、服务代办和授权管理为中心；后端以关系权限、健康时序、事件状态机、审计和适配器为中心；设备/机器人接入层以统一契约、仿真和真实设备验证为中心。

P0 的目标不是证明系统“什么都能做”，而是证明一条事件从产生、分发、响应到关闭的全过程可追踪。只有这条闭环稳定运行，心率趋势、AI 报告、复杂机器人和第三方医疗接入才有增量价值。

互联网诊疗必须由医疗机构承担；AI 报告必须明确辅助、非诊断和可复核属性；健康医疗数据必须遵循最小化、授权、加密和审计原则。对机器人协议、医院 HIS、语音供应商、支付和真实服务供给的不确定性，统一采用 Mock/仿真和适配器隔离，是当前条件下最可控、也最符合责任边界的工程策略。
